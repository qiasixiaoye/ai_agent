# Agent 能力治理：工具与 Skill 优化设计说明

这份说明用于面试表达，也作为本项目后续实现依据。核心观点是：Agent 产品的工具和 Skill 不能只做“能调用”，还要能解释、能授权、能审计、能评估、能下线。

## 1. 为什么要做能力治理

在 Agent 系统里，模型本身只负责理解任务、选择能力、整合结果。真正产生外部副作用的是 Tool、MCP 工具和 Skill。随着能力数量增加，主要风险会从“工具不够多”变成：

- 模型选错工具，导致错误调用；
- 工具参数填错，导致执行失败；
- Skill 内部步骤越权，例如文件写入、外部请求、系统命令；
- 工具结果是对的，但模型总结时遗漏或转述错误；
- 缺少统一评估标准，无法判断一个 Skill 是否真的可上线。

所以这里采用“能力契约 + 运行时守卫 + 全链路评估 + 生命周期治理”的方案。

## 2. 能力分层

项目里把能力分成三类：

1. 原子 Tool  
   单次函数调用，例如天气、预算、图片搜索、PDF 生成。特点是输入输出边界清晰，适合做格式校验和确定性测试。

2. 复合 Skill  
   带有说明文档、输入输出、执行步骤和领域经验的能力。它不是一个普通函数，而是“过程知识 + 工具编排 + 领域约束”的封装。

3. 受管 MCP  
   外部运行时提供的工具目录，需要额外处理网络、第三方 API、超时、熔断和确认机制。

面试可以这样讲：Tool 是原子能力，Skill 是可复用过程，MCP 是外部能力接入协议。治理层要把三者统一成一个能力目录，但执行时仍保留不同风险边界。

## 3. 安全契约

每个 Tool 和 Skill 注册时都应该声明安全契约：

- `riskLevel`：低风险、中风险、高风险；
- `permissionScopes`：本地计算、外部只读、文件读取、文件写入、外部写入、系统命令、私密数据、支付/发布等；
- `sideEffects`：无副作用、本地文件副作用、网络副作用、跨系统副作用；
- `dataSensitivity`：公开数据、用户输入、隐私数据、密钥数据；
- `requiresConfirmation`：是否需要用户二次确认；
- `reviewStatus`：未审计、已审计、需要修复、已阻断；
- `lifecycleStatus`：草稿、灰度、可用、归档、下线。

默认策略是：未声明契约的低风险能力可以展示，但高风险能力必须保守处理；出现系统命令、删除、支付、发布、外部写入等能力时，默认需要确认或阻断。

## 4. 运行时守卫

运行时守卫不替代业务逻辑，它只回答三个问题：

1. 这个能力是否允许被调用；
2. 当前参数是否超出声明范围；
3. 是否需要用户确认。

后续完整版本中，Skill、Agent Tool、MCP 调用都会统一进入 `CapabilityPolicyService`。现阶段先实现契约与审计，为强拦截打基础。

## 5. 评估体系

不同能力不能用同一把尺子评估：

- 确定性工具类：看格式合规率、结果准确率、执行成功率、边界用例通过率；
- 功能任务类：看目标达成度、参数完整度、逻辑一致性、结果稳定性；
- 创作建议类：看硬约束满足率、多维质量评分、偏好对齐度、人工抽样结果。

评估还要做链路归因：

1. 调用层归因：模型有没有选对工具，有没有填对参数；
2. 执行层归因：工具或 Skill 自身有没有正确执行；
3. 整合层归因：模型拿到结果后有没有正确转述、引用和整合。

这样可以避免把所有错误都归到“模型不行”或“工具不行”。

## 6. 闭环治理

审计和评估结果要反哺能力生命周期：

- 低风险问题可以自动生成修复建议；
- 高风险问题触发阻断、回滚或下线；
- 失败案例和用户 bad case 自动沉淀为黄金测试集；
- 长期低调用、低评分、高风险的 Skill 自动归档；
- CI/CD 中可以接入契约审计和黄金集评估，达标后再上线。

## 7. 本项目 Phase 1 落地边界

本轮先实现基础治理能力：

- 后端补齐 Tool/Skill 的安全契约与评估契约字段；
- `SKILL.md` frontmatter 支持声明安全与评估信息；
- 新增能力审计服务与接口，输出缺失契约、高风险、缺少评估用例等问题；
- 前端能力中心展示权限、风险、评估状态和审计问题；
- 保留设计说明，便于面试复述。

本轮不做完整沙箱隔离、系统调用追踪、CI/CD 自动下线。这些属于后续 Phase 2/3。

## 8. 正负样例怎么设计

正负样例不能只围绕已有工具写，否则评估集会被当前实现限制住。更好的做法是按“能力类型”和“风险模式”组织：

- 确定性工具正例：天气查询、计算器、数据库只读查询，输入合法时返回结构化结果；
- 确定性工具负例：参数里混入命令片段、路径穿越、超长输入，系统应拒绝或忽略越权部分；
- 高风险工具负例：系统命令、删除、发布、支付等，默认要求确认或直接阻断；
- 创作型 Skill 正例：围绕指定主题输出结构完整、边界清晰的内容；
- 创作型 Skill 负例：用户要求编造指标、夸大生产规模、伪造客户案例时，Skill 应拒绝编造并改为事实边界表达。

面试表达重点：正负样例不是“测试某个函数能不能跑”，而是覆盖模型选工具、参数填充、执行安全和结果整合的关键失败模式。

## 9. localStorage 会话持久化修复思路

这次定位到的根因是：之前 localStorage 的恢复逻辑写在 `ChatWorkspace` 里。刷新到 `/capabilities`、`/knowledge-base` 这类非 Chat 页面时，Chat 组件不会挂载，所以 Pinia 里的会话 Store 不会从 localStorage 恢复，Inspector 和其他页面自然显示不到当前会话。

修复方式是把恢复和写入上移到 `WorkbenchLayout`：

- Layout 初始化时先读取 localStorage，恢复 `chatStore` 和 `workbenchStore`；
- 任意页面刷新都能拿到 `currentConversationId` 和历史消息；
- Chat 页面只负责选择当前会话或创建新会话，不再重复读写 localStorage；
- 写入逻辑统一监听全局工作台状态和聊天 Store，避免多个页面重复写。

面试表达重点：状态持久化不能绑在某个页面组件生命周期上，应该放在应用壳层或全局会话管理层，否则刷新到非目标页面时会出现“存了但没恢复”的假持久化问题。
