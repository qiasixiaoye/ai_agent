# 统一 Agent 编排与事件驱动记忆设计

## 1. 背景与目标

当前系统把普通对话、知识库问答和 Agent 执行拆为多条接口与前端模式。特别是 Manus 链路会把 `Step N: 工具返回结果` 当作聊天文本流式输出；前端又从完整回复中截取候选记忆。这会导致原始 Tool 输出污染回复，也可能被错误写入长期记忆。

第一期将它们统一为同一个会话入口：用户只描述目标，系统自动决定是否直接回答、检索知识库、调用 Tool、调用 Skill，或组合执行。对话只展示最终答案，执行过程和记忆写入以结构化、可审计的事件呈现。

### 成功标准

- 用户不需要先选择“普通对话 / 知识库 / 智能体”才能得到合适能力。
- Tool、检索、Skill 的原始结果不再作为 AI 聊天消息显示。
- 记忆仅消费已完成轮次的结构化信息，不保存原始工具输出和流式中间片段。
- Tool 与 Skill 的现有权限、审计、调用入口保持可用，迁移以适配层完成。
- 聊天页不再展示 UUID、原始候选记忆、上下文预算等调试信息；这些信息保留在 Memory 与 Observability 页面。

## 2. 范围与非目标

### 本期范围

1. 增加统一编排入口与路由决策。
2. 将会话流改为带类型的 SSE 事件，并保留最终答案的流式体验。
3. 用结构化候选记忆替代前端字符串拼接。
4. 简化聊天页执行与记忆信息展示。
5. 为 Tool、Skill、RAG 输出增加统一的证据和执行结果适配层。

### 本期非目标

- 不替换现有 RAG、MCP、Tool 或 Skill 的底层实现。
- 不引入新的外部向量库、消息队列或专用记忆模型服务。
- 不做全自动 Skill 上下线、自动修复、灰度发布；这些复用现有治理模型并在后续迭代。
- 不把用户的敏感信息默认写入长期记忆。

## 3. 方案选择

选择“统一编排器 + 确定性策略门 + 结构化事件”的方案。

- 不采用让模型直接在全量能力中任意调用的方案：该方案难以约束权限、成本和审计。
- 不采用只靠关键词路由的方案：关键词可作为快速拦截，但无法覆盖复合问题和上下文。

编排器首先使用确定性规则排除明显不需要执行能力的问题，并根据能力契约筛选候选。只有在候选不唯一或问题为复合任务时，才请求模型输出受 JSON Schema 约束的执行计划。计划仍必须通过权限策略和参数校验才能执行。

## 4. 架构与职责

### 4.1 请求编排器 `RequestOrchestrator`

输入为会话 ID、用户消息和可选的用户确认结果；输出为执行计划、事件流和最终回答。

它不实现搜索、RAG、Tool 或 Skill 本身，只负责：

1. 组装与当前问题相关的上下文和长期记忆。
2. 产生并校验路由计划。
3. 通过策略门执行已批准的能力。
4. 将证据交给回答汇总器。
5. 在最终回答完成后发布记忆候选事件。

### 4.2 路由与策略门 `CapabilityRouter` / `CapabilityPolicy`

路由类型固定为：`DIRECT`、`KNOWLEDGE`、`TOOL`、`SKILL`、`MIXED`。

策略门复用能力治理资料，至少校验风险等级、权限范围、是否需要确认、参数 Schema、调用预算和可用状态。路由决策不等于授权：高风险能力即使被选中，也必须在执行前得到用户确认。

### 4.3 统一能力适配器 `EvidenceAdapter`

所有检索、Tool 与 Skill 执行结果被转换为统一的 `Evidence`：

```json
{
  "sourceType": "knowledge|tool|skill",
  "sourceId": "web-search",
  "status": "success|empty|failed|blocked",
  "summary": "可展示的简短结论",
  "provenance": {"reference": "可追溯来源", "freshness": "可选时间"},
  "payload": "仅供后续模型与审计使用的受限内容"
}
```

`payload` 不直接进入聊天 UI；`summary` 也只作为执行过程摘要。对于搜索无结果，状态为 `empty`，而不是向用户回显多条 `No web results`。

### 4.4 回答汇总器 `AnswerSynthesizer`

汇总器基于用户问题、已选上下文和 `Evidence` 生成最终回答。其约束为：

- 不输出内部 Step、完整 Tool 返回值或调用参数；
- 证据不足时明确说明限制，并给出可行的下一步；
- 回答包含必要的来源或调用说明，但不伪造已检索到的信息；
- 只有 `final_delta` 可作为 AI 消息追加到对话记录。

### 4.5 记忆流水线 `MemoryCandidatePipeline`

记忆按事件触发，而不是按每个流式片段触发：

1. `ConversationTurnCompleted` 在最终回答完成后发布。
2. 提取器从用户问题、最终回答、执行摘要中生成结构化候选。
3. 策略层负责置信度、敏感性、去重、冲突和过期时间。
4. 满足“高置信、非敏感、稳定”的候选自动写入；其他候选等待用户确认。
5. 任务完成、会话空闲或达到固定轮次时进行摘要与语义合并。

候选类型为：`preference`、`profile_fact`、`task_state`、`project_decision`、`tool_experience`。禁止写入：原始 Tool 响应、临时闲聊、单次猜测、未验证事实、敏感个人数据。

现有分层记忆继续负责持久化和按问题检索；本期新增的是其前面的候选提取、策略和事件边界。

## 5. 事件协议

SSE 采用显式事件名和 JSON 数据，代替将所有过程拼成字符串。

| 事件 | 目的 | 聊天区行为 |
| --- | --- | --- |
| `request_started` | 请求开始、关联 trace | 显示加载状态 |
| `route_selected` | 已选择直接回答、知识、Tool、Skill 或组合 | 显示简短状态 |
| `retrieval_completed` | 检索结果数、状态和摘要 | 只更新过程面板 |
| `capability_started` | 经策略门批准的能力开始 | 只更新过程面板 |
| `capability_completed` | 能力完成、失败或无结果 | 只更新过程面板 |
| `confirmation_required` | 高风险能力等待用户确认 | 显示确认卡片 |
| `final_delta` | 最终回答增量 | 追加 AI 消息 |
| `final_completed` | 最终回答完成 | 固化消息并启动记忆流程 |
| `memory_candidate` | 生成、写入或跳过记忆 | 更新记忆状态 |
| `request_failed` | 不可恢复失败 | 展示可理解错误和重试入口 |

每个事件都带有 `conversationId`、`requestId` 和 `traceId`。前端按 `requestId` 合并事件，避免并发请求的状态串台。

## 6. 端到端数据流

1. 前端发送用户消息到统一会话端点，并立即创建 `requestId`。
2. 编排器读取短期上下文和与问题相关的长期记忆。
3. 路由器生成受限计划，并发送 `route_selected`。
4. 编排器按计划执行 RAG、Tool、Skill；所有结果经 `EvidenceAdapter` 标准化。
5. 汇总器只以受控证据生成最终回答，并发出 `final_delta` 与 `final_completed`。
6. 轮次完成事件异步触发候选记忆；写入决策不阻塞最终回答。
7. 事件、能力调用和记忆决策共享 `traceId`，供 Observability 查询。

## 7. 前端交互

聊天页只保留一个“自动编排”会话入口。原先的普通对话、知识库和智能体标签不再决定服务端路径；如有需要，可作为高级设置中的“偏好/限制”，例如“本轮不调用外部 Tool”。

右侧栏替换为紧凑的运行概览：

- **本轮执行**：如“已检索知识库”“已调用 1 个 Tool”“无需外部能力”。
- **记忆状态**：如“未产生可写记忆”“已自动保存 1 条，可撤销”“有 1 条待确认”。
- **查看详情**：跳转 Trace、Memory 管理与 Observability。

会话 UUID、候选原文、上下文 token 预算、原始执行日志只放在调试/管理页面，不占用正常聊天空间。

## 8. 异常与安全策略

- Tool 无结果：转为 `empty` 证据；汇总器说明信息不足，不重复打印底层错误。
- Tool 失败：转为 `failed` 证据；允许策略定义的重试或降级，但不得把异常堆栈暴露给用户。
- 权限不足或高风险操作：发出 `confirmation_required`，未确认不执行。
- 记忆提取失败：记录 Trace 并跳过本轮写入，不影响回复。
- 请求中断：停止当前 `requestId` 的事件消费，不将不完整回复写入长期记忆。

## 9. 验收与测试

### 自动化验证

- 路由：直接问题、知识问题、实时信息问题、复合任务分别得到正确计划类型。
- 事件：Tool 结果不会出现在 `final_delta`；事件均包含三类关联 ID。
- 权限：需要确认的能力无法在未确认状态下执行。
- 记忆：原始 Tool 结果与中间事件不能形成候选记忆；高置信稳定偏好可自动写入；重复候选会合并。
- 兼容：现有 Tool、Skill、RAG 和本地会话恢复测试继续通过。

### 页面验收

- 用户无需切换模式即可得到检索或能力调用。
- AI 气泡只展示组织后的回答，不出现 `Step N` 或 `工具:xxx返回结果`。
- 右侧栏不展示 UUID、原始文本框或 token 预算。
- 执行过程可展开查看，Trace 可从本轮跳转。

## 10. 后续迭代

第一期稳定后，再扩展：能力成功率与成本指标、异常自动熔断、Skill 灰度发布、失败案例回灌评估集、记忆的人工审查与版本回滚。它们依赖本期统一 trace、能力契约和事件协议，因此不提前耦合进首版。

## 11. 面试表达要点

可以将这一设计概括为：

> 我把模式驱动的聊天产品改成了目标驱动的 Agent 编排系统。用户只表达任务，后端通过受约束的路由计划选择 RAG、Tool 或 Skill；执行结果先标准化为证据，再由汇总器输出答案。全链路以事件和 trace 关联，既避免工具原始输出污染对话，也让权限、审计、失败降级和长期记忆有明确边界。记忆不是把聊天全文塞进向量库，而是从完成轮次中提取稳定、可复用、非敏感的候选信息，再做去重、置信度判断和异步合并。
